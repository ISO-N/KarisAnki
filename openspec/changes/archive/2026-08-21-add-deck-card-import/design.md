## Context

现有卡组详情页只有单张创建卡片入口，后端 `CardService.create` 会为每张新卡创建 `Card` 和 `CardState`。导入功能需要增加批量输入、预览编辑和批量落库，同时沿用现有权限隔离、新卡状态和 Markdown 内容模型。

## Goals / Non-Goals

**Goals:**

- 用一个后端解析入口同时覆盖粘贴 JSON 和上传 `.json` 文件。
- 解析返回逐项可编辑预览，不把 JSON 解析逻辑放在前端。
- 导入接口重新校验并原子写入，重复现有卡片时跳过。
- 导入卡片成为新卡并保留文件顺序。

**Non-Goals:**

- 不做数据库唯一约束或跨用户去重。
- 不导入调度进度、复习历史或图片文件本身。
- 不做 CSV、Anki `.apkg` 等其他格式。
- 不持久化未提交的导入草稿。

## Decisions

### 1. 原始文本解析接口，不上传 multipart

`POST /api/decks/{deckId}/cards/parse` 接收 `{ "source": "..." }`，前端上传文件时用 `FileReader` 读取文本后走同一个接口。

- 理由：粘贴和文件只有来源不同，后端解析、校验、去重逻辑只有一份。
- 备选：单独支持 multipart 文件接口，会引入两条上传路径和两套大小限制，收益不大。

### 2. 解析与导入都是无状态接口

解析返回预览后，前端在本地编辑行。最终导入时前端把编辑后的卡片数组发给 `POST /api/decks/{deckId}/cards/import`，后端重新解析、校验和去重。

- 理由：不需要服务端保存临时预览状态，刷新或离开页面不会留下过期数据。
- 备选：用解析 token 引用服务端预览，需要管理临时状态，且编辑后仍要重新提交。

### 3. 解析采用逐行错误，不整批失败

解析接口对无效行返回 `errors`，只有 JSON 非数组、JSON 语法错误或超过限制时才返回请求级错误。

- 正面缺失、空白或类型错误返回 `front_required`。
- 背面缺失或空白归一化为空字符串；如果出现但类型不是字符串，返回 `back_invalid`。
- 未知字段忽略。

### 4. 重复检测以当前卡组活动卡片为准

去重键是规范化后的 `front` + `back`：`front` trim，`back` 空白归一化为空字符串，比较区分大小写。

- 仓库层用投影查询只加载活动卡片的 `front`、`back`，避免加载整个实体。
- 只匹配当前用户、当前卡组、未删除的卡片。
- 同一份文件内部出现相同行时不做文件内去重，除非该内容已存在于当前卡组。
- 备选：添加数据库唯一约束，能解决并发重复，但会要求迁移并处理历史重复数据，超出本次范围。

### 5. 批量导入在一个事务内完成

`CardService` 新增批量导入方法：

1. 校验用户对卡组的访问权限。
2. 校验并规范化全部卡片；存在无效行时直接抛错，不写入。
3. 加载当前卡组活动卡片内容用于去重。
4. 从 `maxPosition + 1` 开始为每张新卡分配连续 position。
5. 批量创建 `Card` 和 `CardState`，新卡状态与单张创建一致。
6. 返回 `created` 和 `skippedDuplicates`。

`@Transactional` 保证任何失败都回滚，不会出现部分导入。

### 6. 导入限制通过配置控制

在 `AppProperties` 增加 `karisanki.import.max-source-bytes` 和 `karisanki.import.max-cards`，默认建议 `2MB` 和 `5000` 张。

- 后端在解析前检查原始文本长度，在解析后检查卡片数量。
- 前端文件选择时做同样大小提示，但以后端为准。
- 超出限制返回 `import_source_too_large` 或 `too_many_import_cards`。

### 7. 前端用独立导入面板

在卡组详情页 `PageHeader` 增加“导入卡片”按钮，打开右侧 `Sheet` 面板。面板包含：

- “粘贴 JSON / 上传文件”两个入口。
- 解析按钮和解析摘要。
- 可滚动预览列表，每行有正面、背面输入框、状态标记和删除按钮。
- 底部“新增一行”和“导入”按钮。

预览编辑不触发重新解析；用户修改后直接点击导入，后端会重新校验。导入成功后关闭面板并刷新卡片列表。

### 8. 错误码走现有前端映射

后端新增错误码：`invalid_import_json`、`import_source_too_large`、`too_many_import_cards`、`front_required`、`back_invalid`。`front_required` 已存在，前端逐行错误直接复用；其他错误在 `api.ts` 和 `i18n.tsx` 补充中英文文案。

## Risks / Trade-offs

- 应用层去重在并发导入下可能竞态，理论上仍会重复 → 保持 `@Transactional`，单实例单用户场景风险低；未来如需更强保证再评估唯一约束。
- 单批最多 5000 行时前端渲染大量可编辑输入框可能变慢 → 限制卡片数量，预览使用可滚动容器，不在行内默认渲染 Markdown。
- 解析阶段和导入阶段都可能做一次重复检测 → 这是为了校验预览后状态变化，成本可接受。
- 文件内容直接进入 JSON 解析器，恶意或异常大的内容可能增加请求处理成本 → 在解析前用配置限制原始文本大小。

## Migration Plan

无数据库迁移。后端和前端在同一版本部署，先构建镜像并重启 `backend`，再更新 `frontend`；若需回滚，回退代码并重建镜像，不涉及数据清理。导入失败不会改变已有数据。
