## Purpose

定义客户端缓存优先加载、API 响应合并和批量答题提交行为，以减少前后端网络开销，同时保持服务端对调度结果和答题状态拥有最终权威。

## ADDED Requirements

### Requirement: 缓存优先 API 数据加载

系统 SHALL 允许已认证客户端在重复访问时，先用本地缓存的用户资料、卡组列表、卡片列表、统计和会话快照渲染页面，同时在后台向服务端重新校验数据。服务端响应 SHALL 始终作为最终数据来源，并在返回后替换本地缓存。

#### Scenario: 重复访问 Dashboard

- **WHEN** 用户返回 Dashboard 且客户端已有缓存卡组数据
- **THEN** Dashboard 立即使用缓存卡组数据渲染
- **AND** 客户端在后台请求最新卡组数据
- **AND** 最新响应到达后更新页面显示

#### Scenario: 弱网且存在缓存

- **WHEN** 网络不可用或较慢，且客户端有所请求视图的缓存数据
- **THEN** 客户端继续使用缓存数据渲染
- **AND** 页面不会替换为空白加载状态或错误状态

#### Scenario: 没有缓存数据

- **WHEN** 用户首次打开某视图且本地不存在缓存
- **THEN** 视图先从服务端请求数据再渲染内容
- **AND** 现有加载状态和错误状态仍然可用

### Requirement: 缓存隔离与失效

系统 SHALL 将所有缓存 API 数据限制在已认证用户范围内，并在退出登录或成功执行数据变更操作后清除或失效相关缓存。一个用户的缓存数据 SHALL NOT 被另一个用户看到。

#### Scenario: 数据变更后刷新缓存列表

- **WHEN** 用户创建、重命名、删除或重置卡组/卡片
- **THEN** 受影响的缓存列表和详情数据被失效或更新
- **AND** 后续缓存读取不再显示变更前的状态

#### Scenario: 退出登录清除用户缓存

- **WHEN** 用户退出当前设备
- **THEN** 该用户作用域下的缓存 API 数据被清除或对后续账号不可访问

#### Scenario: 答题同步更新缓存会话

- **WHEN** 服务端接受一条答题提交
- **THEN** 客户端更新缓存中的会话队列和相关 Dashboard 计数
- **AND** 已接受的答题不会再次提交

### Requirement: Dashboard bootstrap API

系统 SHALL 提供已认证 bootstrap 接口，在单个响应中返回当前用户资料和带到期计数的卡组列表。现有 `/api/auth/me` 与 `/api/decks` 接口 SHALL 继续保留以保持向后兼容。

#### Scenario: Dashboard 单请求

- **WHEN** 已认证用户打开 Dashboard 且客户端选择使用 bootstrap 接口
- **THEN** 客户端在单个响应中同时获得当前用户和卡组列表
- **AND** Dashboard 可以直接从该响应渲染

#### Scenario: 向后兼容

- **WHEN** 客户端不使用 bootstrap 接口
- **THEN** 客户端仍可通过现有接口加载用户资料和卡组列表
- **AND** 现有接口行为不发生改变

### Requirement: 卡组详情概览 API

系统 SHALL 提供已认证卡组概览接口，在单个响应中返回卡组摘要、计数和所请求的卡片分页。该响应 SHALL 与现有卡片列表接口保持相同的搜索、状态筛选和分页行为。

#### Scenario: 卡组详情单请求

- **WHEN** 已认证用户打开卡组详情页并携带搜索词、状态筛选和页码
- **THEN** 客户端可以从一个接口获得卡组摘要和匹配的卡片分页
- **AND** 页面无需加载完整卡组列表来识别当前卡组

#### Scenario: 无权访问卡组

- **WHEN** 已认证用户请求无权访问的卡组概览
- **THEN** 系统返回与现有卡组接口相同的授权失败或资源不存在行为

### Requirement: 批量答题提交

系统 SHALL 接受同一已认证用户和同一会话上下文的按序批量答题，对每条答题应用现有调度和幂等语义，并逐项返回结果。每条答题 SHALL 保留其 `clientAnswerId`、状态版本和前置答题链校验。

#### Scenario: 批量同步待同步答题

- **WHEN** 客户端在单个批量请求中提交同一会话的多条待同步答题
- **THEN** 服务端按提交顺序处理条目
- **AND** 对每条成功应用的回答返回已接受结果
- **AND** 已接受的条目在重试时不会再次应用

#### Scenario: 批量中的部分冲突

- **WHEN** 批量中的一条回答未通过状态或队列校验
- **THEN** 服务端对该条返回冲突结果
- **AND** 同批次中其他有效条目保持已接受
- **AND** 客户端只处理冲突条目，无需重新提交已接受条目

#### Scenario: 批量幂等

- **WHEN** 相同 `clientAnswerId` 在同一个批次或不同批次中重复出现
- **THEN** 服务端只应用一次答题状态和答题事件
- **AND** 后续重复出现时返回此前已接受的结果

### Requirement: 在线评分同步不阻塞

系统 SHALL 在每条评分进入网络提交前先在本地持久化，并 SHALL 允许用户在有待批量同步评分时继续评分。网络失败 SHALL 使评分保持待同步状态，且 SHALL NOT 回滚本地进度。

#### Scenario: 同步期间继续评分

- **WHEN** 用户评分一张卡片，而之前评分仍在批量同步队列中
- **THEN** 用户立即进入下一张卡片
- **AND** 待同步评分继续等待服务端确认

#### Scenario: 同步时网络失败

- **WHEN** 批量答题请求因网络错误失败
- **THEN** 该批次全部条目保持待同步状态
- **AND** 客户端稍后重试且不丢失本地进度
